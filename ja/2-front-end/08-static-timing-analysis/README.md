# 第 8 章　静的タイミング解析：すべてのパスが間に合わなければならない

> 📍 **設計の現在地**
>
> - 前の工程：論理合成。`mac` はセル 865 個になった
> - **この章：`mac` が 500 MHz に間に合うかを確かめ、パイプラインを 1 段入れる**
> - 次の工程：テスト容易化設計。壊れたチップを工場で見つけられるようにする

🪜 抽象度：仕様 ▸ RTL ▸ **ネットリスト** ▸ レイアウト ▸ GDS ▸ チップ

---

## リレー：データは次の笛までに着かなければならない

クロックのエッジごとに、フリップフロップはデータを送り出します。データは一連の組み合わせ回路を通り抜け、次のクロックのエッジより前に、次のフリップフロップに着かなければなりません。リレー競走に似ています。どの走者も、笛が鳴る前に次の走者へバトンを渡さなければなりません。

バトンの受け渡しには、さらに二つの決まりがあります。

- **Setup**：クロックのエッジより前に、データが少しの間安定していなければならない。そうでないとフリップフロップはきれいに撮れない。
- **Hold**：クロックのエッジのあとも、データは少しの間変わらずにいなければならない。次のデータにすぐ上書きされてはいけない。

だから setup の要求は次のように書けます。**クロック周期 ≥ フリップフロップの出力遅延 ＋ 組み合わせ回路の遅延 ＋ setup 時間**。

![タイミング図：クロックの立ち上がりエッジの前後に、データが安定していなければならない時間がある](../../../images/08-setup-hold.svg)

*図の説明：上がクロック、下がデータ。① クロックの立ち上がりエッジ。② setup 時間。③ hold 時間。④ データが安定している期間で、② と ③ を完全に覆っていなければならない。⑤ データが変わる時刻で、② と ③ の外にしか置けない。*

> [!NOTE]
> **📖 用語｜Setup と Hold（Setup 與 Hold）**
>
> - **定義**：setup time はクロックのエッジより前にデータが安定していなければならない時間で、hold time はクロックのエッジのあとにデータが変わらずにいなければならない時間である。
> - **現場での使い方**：「setup が通らなければ周波数を下げればいい。hold が通らなければ、チップは使えない」。
> - **関連用語**：スラック、クリティカルパス、クロックスキュー
> - **よくある混同**：setup 違反はクロック周波数に関係し、周波数を下げれば解決できる。hold 違反は周波数に関係せず、周波数を下げても救えない。

## 静的：入力のいらないタイミング解析

シミュレーションには入力が必要で、しかもすべてのパスを試すことはできません。**静的タイミング解析**（Static Timing Analysis、STA）は別のやり方を取ります。入力は何も流さず、ライブラリにある各セルの遅延を調べ、配線ごとの遅延を見積もって、チップのすべてのパスの遅延を 1 本ずつ足し合わせます。

チップには数百万本、ときには数十億本のパスがありますが、STA は数時間ですべてを確かめられます。

> [!NOTE]
> **📖 用語｜静的タイミング解析（Static Timing Analysis、STA、靜態時序分析）**
>
> - **定義**：テストの入力を必要とせず、パスごとに遅延を計算して、setup と hold を満たしているかを確かめる方法。
> - **現場での使い方**：「STA が終わったけど、WNS はまだ -0.12 ns だ」「このパスは STA で false path に設定して」。
> - **関連用語**：スラック、WNS、TNS、タイミング制約
> - **よくある混同**：STA が見るのはタイミングだけで、機能は見ない。論理を書き間違えていても、STA はすべて通ることがある。

## スラック：あとどれだけ時間が残っているか

どのパスにも「遅くともこの時刻までに着かなければならない時刻」と「実際に着いた時刻」があり、その差が**スラック**（slack）です。

- スラックが正：データは早く着いており、まだ余裕がある。
- スラックが負：データが遅刻しており、このパスは違反している。

スラックが最も悪いパスを**クリティカルパス**（Critical Path）と呼び、チップがどれだけ速く動けるかはこれで決まります。レポートで最もよく見る数字は **ワーストネガティブスラック**（Worst Negative Slack、WNS）と**トータルネガティブスラック**（Total Negative Slack、TNS、すべての負のスラックの合計）の二つです。WNS は最悪のパスがどれだけ足りないかを、TNS は問題がどれだけ広がっているかを示します。

---

## プロセスコーナー：いちばん遅いチップでも間に合わなければならない

同じ設計から作ったチップでも、速さはまったく同じにはなりません。プロセスにはばらつきがあり、電圧は下がり、温度も変わります。だから STA は 1 回計算すれば終わりではなく、いくつもの極端な条件でそれぞれ計算します。この条件を**プロセスコーナー**と呼びます。

- **setup** はふつう最も遅いコーナーで確かめる。トランジスタは遅め、電圧は低め、温度は高め。
- **hold** はふつう最も速いコーナーで確かめる。トランジスタは速め、電圧は高め、温度は低め。

比較的新しいプロセスには、低電圧のとき、直感に反する現象もあります。低温でかえって回路が遅くなるもので、**温度逆転**（Temperature Inversion）と呼びます。28 nm クラスの `tiny_npu` も、これを考慮しなければなりません。だから確かめるべきコーナーは、直感で思いつくより多くなります。同じチップの中の場所による違いは、**オンチップばらつき**（On-Chip Variation、OCV）として、別に余裕を加えて扱います。

> [!NOTE]
> **📖 用語｜プロセスコーナー（Process Corner、製程角落）**
>
> - **定義**：プロセス、電圧、温度（PVT）の極端な値を組み合わせた解析条件。
> - **現場での使い方**：NMOS と PMOS の速さを 2 文字で表す。「SS コーナーで setup が通らない」「FF コーナーで hold を見る」。
> - **関連用語**：PVT、OCV、マルチコーナー・マルチモード解析（MCMM）
> - **よくある混同**：コーナーはウェーハの隅のことではなく、プロセス、電圧、温度を組み合わせた極端な状況のことである。

<details>
<summary>🔍 もう一歩深く：なぜ hold はクロック周波数に関係しないのか</summary>

setup が比べるのは、このクロックで送り出したデータが、**次の**クロックのエッジより前に着けるかどうかです。間には周期がまるごと一つあるので、周期が長くなれば setup は満たしやすくなります。

hold が比べるのは、このクロックで送り出した新しいデータが早く着きすぎて、**同じ**クロックのエッジで、次のフリップフロップがまだしっかり撮りきっていない古いデータを上書きしてしまわないかどうかです。送り出しと受け取りが同じエッジで起きるので、式の中に周期という項がそもそもありません。

だから hold 違反は、主にデータパスを長くすることで直します。たとえば遅延用のバッファを挿入します。チップができてしまえば、電圧や温度を変えて少し影響を与えられるだけで、手の打ちようはほとんどありません。

</details>

## mac は間に合わない：パイプラインを 1 段入れる

`mac` のクリティカルパスは、入力の `a` と `b` から出発し、乗算器と加算器を通って、累算器のフリップフロップに着きます。`tiny_npu` では、`a` と `b` は SRAM が 1 クロックごとに送り出すデータで、これもフリップフロップから来ています。論理合成のあと、このパスは最長で 32 段の論理ゲートを通ります。1 段の平均が 70 ps なら、論理だけで 2.24 ns となり、500 MHz の周期 2 ns をすでに超えています。

直し方は、乗算器と加算器の間にフリップフロップを一列入れ、長いパスを二つに分けることです。これを**パイプライン**（Pipeline）と呼びます。これが `rtl/mac_ch08.v` の前半です。

```verilog
    // Stage 1: multiply, and delay the control signals to match.
    reg signed [15:0] prod;
    reg               clr_d, en_d;
    always @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            prod  <= 16'sd0;
            clr_d <= 1'b0;
            en_d  <= 1'b0;
        end else begin
            prod  <= a * b;
            clr_d <= clr;
            en_d  <= en;
        end
    end
```

後半で `prod` を累算器に足し込みます。最長のパスは 32 段から 24 段に減りました。いま最も長いのは乗算器の区間で、加算器から累算器に戻る輪はずっと短くなっています。その代わりにフリップフロップが 18 個増え（16 ビットの積と、1 クロック遅らせる二つの制御信号）、結果も 1 クロック遅れて出てきます。つまり**レイテンシ**（Latency）が 1 クロックから 2 クロックになりました。それでも 1 クロックに 1 回の積和演算を終えることに変わりはないので、**スループット**（Throughput）は同じです。

> [!IMPORTANT]
> **💻 ソフトウェアとの対比｜パイプラインは CPU の命令パイプラインに似ているが、遅延の面倒は誰も見てくれない**
>
> - **似ている点**：CPU は 1 個の命令をいくつかの段階に分け、生産ラインのように何個もの命令を同時に処理する。
> - **違う点**：RTL にパイプラインを 1 段入れたら、「何クロック後に結果が出るか」に頼っているすべての場所を直さなければならない。制御回路は 1 クロック多く待ち、テストベンチは 1 クロック遅れて比べ、ファームウェアの前提も更新が必要かもしれない。自動で調整してくれるものは何もない。
> - **だから注意**：パイプラインの深さを変えたら、それに頼っているすべての場所を探し出し、検証をやり直す。やってみようでは、テストベンチを直さないと何が起きるかを見る。

## タイミングクロージャ

すべての違反を直し、スラックがどこも負でなくなるまで持っていくことを、**タイミングクロージャ**（Timing Closure）と呼びます。よく使う手段は、RTL のアーキテクチャを変えたりパイプラインを入れたりすること、セルを駆動力の大きいものに替えること、クリティカルパス上のセルを低 Vt のものに替えることです。hold 違反には遅延用のバッファを挿入します。

論理合成のあとの STA では、配線の遅延は見積もりでしかありません。第 12 章で本物の配線をつないだあと、抽出した値でもう一度行います。

> [!TIP]
> **🔧 ノウハウ｜大きなタイミングの問題は RTL の段階で解決する**
>
> - **状況**：論理合成のあとの STA で、クリティカルパスが数百ピコ秒足りないとわかった。
> - **やり方**：RTL に戻ってアーキテクチャを変えるか、パイプラインを入れる。論理合成の段階で周期の一部を残しておき、あとで加わる配線遅延の余裕にする。
> - **理由**：バックエンドのツールが得意なのは、セルの大きさや位置の調整のような小さな違反の修正である。大きく足りないパスは、論理の構造を変えるしかない。
> - **やらないとどうなる**：バックエンドが何週間も試行錯誤を繰り返し、結局は RTL に戻って直すことになり、日程がすべて後ろにずれる。
> - **関連する章**：[第 12 章　配線と寄生成分](../../3-physical-design/12-routing-and-parasitics/README.md)

> [!TIP]
> **🔧 ノウハウ｜hold 違反はテープアウト前に必ずすべてなくす**
>
> - **状況**：テープアウトの直前、ほんの少しだけ足りない hold 違反が何本かあり、誰かが放っておこうと言い出す。
> - **やり方**：どのコーナーでも、hold は違反がなくなるまで直す。「戻ってきたら周波数を下げればいい」という考えは持たない。
> - **理由**：setup が足りなければ周波数を下げて使える。hold は周波数に関係しないので、周波数を下げても意味がない。
> - **やらないとどうなる**：チップが戻ってきたあと、どれだけ遅く動かしても誤動作し、マスクを作り直すしかなくなる。
> - **関連する章**：[第 13 章　サインオフ](../../3-physical-design/13-signoff/README.md)

## 🧪 やってみよう：論理段数を比べ、パイプラインを検証する

この練習では本物のライブラリの遅延データをつないでいないので、ここでは**論理段数**（パス上で何段の論理ゲートを通るか）を遅延の代わりに使います。`practice/` フォルダで、パイプラインを入れる前とあとの最長パスを比べます。

```bash
yosys -q -p "read_verilog rtl/mac_ch06.v; synth -top mac; tee -o /dev/stdout ltp -noff" | grep Longest
yosys -q -p "read_verilog rtl/mac_ch08.v; synth -top mac; tee -o /dev/stdout ltp -noff" | grep Longest
```

```text
Longest topological path in mac (length=32):
Longest topological path in mac (length=24):
```

Yosys の版が違えば、論理段数は少し変わることがあります。次に、第 6 章のテストベンチで、パイプライン版の `mac` をテストします。

```bash
iverilog -o sim rtl/mac_ch08.v tb/tb_mac.v
vvp sim +vec=vectors/random.txt
```

```text
MISMATCH at line 2: a = -127, b = -49, expected 6223, got 0
MISMATCH at line 3: a = 80, b = 50, expected 10223, got 6223
MISMATCH at line 4: a = -12, b = -73, expected 11099, got 10223
FAIL: 188 of 208 checks failed
```

`mac` は計算を間違えていません。3 行目で得た 6,223 は、まさに 2 行目の答えです。結果が 1 クロック遅れているのに、テストベンチはもとのタイミングで比べています。レイテンシが 2 クロックになったことをテストベンチに伝えて、もう一度流します。

```bash
iverilog -P tb.LAT=2 -o sim rtl/mac_ch08.v tb/tb_mac.v
vvp sim +vec=vectors/random.txt
```

```text
PASS: 208 of 208 checks passed
```

このパイプライン版が、このあとテープアウトする版です。

## この章のポイント

1. データは次のクロックのエッジより前に着き、setup と hold を満たさなければならない。周期はパス上の遅延の合計より長くなければならない。
2. STA は入力を必要とせず、パスごとにスラックを計算し、複数のプロセスコーナーで確かめる。
3. setup 違反は周波数を下げれば解決できるが、hold 違反は周波数に関係しないので、テープアウト前に必ずなくす。
4. `mac` は 500 MHz ではパスが長すぎる。パイプラインを 1 段入れると、論理段数は 32 段から 24 段に減り、結果は 1 クロック遅れて出てくる。
5. パイプラインの深さを変えたら、レイテンシに頼っているすべての場所を直し、検証し直す。
